# ローカル実行を任意にする仕様検討案

状態：設計提案。Driveへの書き込みや、クラウドでの初期構築の実機検証は行っていない。

## 決めたい基本仕様

PMOの利用に、ユーザーのPC、Python、Drive for Desktop、定期ジョブを必須にしない。共通のMarkdown原本を、ChatGPT＋Google Driveプラグイン、Claudeアプリ＋Google Driveコネクター、ローカルCLIから扱う方法を用意する。

「PCで実行しない」と「一切コードを実行しない」は別。利用するAIアプリの作業環境で一時ファイルを生成し、そのアプリのDrive接続で保存する経路は許容する。利用者自身のPCにPMOを導入する必要はない。利用中のアプリに必要なファイル生成・アップロード機能がなければ、未完了として伝える。

| 操作 | クラウド経由で目指す動作 | ローカルCLI |
|---|---|---|
| 初期構築 | GitHubの公開済み固定版を読む→Driveへ配置→読み戻す | `pmo install` |
| 記憶・訂正 | 指示された内容を原本へ保存 | `record` / `correct` / `ingest-turn` |
| 記憶の一覧更新 | 会話中の指示・受け入れられた提案に応じて更新 | `rebuild` |
| 日次要約 | 対象日のログを読み、指示されたときに生成 | `daily` |
| 検索 | Driveで候補を探し、原本を読む。完全性を保証しない | SQLite FTS。現在は明示的に再生成 |
| システム更新 | 新旧版と変更内容を確認して、指示されたときに適用 | パッケージ更新後に`update` |
| 定期処理 | 必須ではない。別途ユーザーが設定した場合だけ | 任意の追加運用 |

これは機能目標の比較であり、クラウド経路の実装完了を意味しない。

## ChatGPT・Claudeアプリからの初期構築

ChatGPTとClaudeアプリを同等の初期構築入口にする。Claude Codeの導入やローカルMCPサーバーを前提にしない。READMEに「ChatGPTで始める」「Claudeアプリで始める」の導線を並べ、共通のセットアップ手順を使う。

| 入口 | Driveへの接続 | 初期構築後に提示する指示の登録先 |
|---|---|---|
| ChatGPT | Google Driveプラグイン | カスタム指示 |
| Claudeアプリ | Google Driveコネクター。必要な操作がなければ、対応するリモート接続を案内 | 全会話で使うならプロフィール指示、指定プロジェクト内だけならプロジェクト指示 |

どちらから作っても同じvault構造・schema・Configになる。既存vaultをもう一方のアプリへ接続するときは再構築せず、入口の読み取りと利用可能な操作を確認して、そのアプリ用の指示文を提示する。サービスごとに記憶のコピーを作らない。

共通の依頼文は以下。ChatGPT向けには「Drive接続」を「Google Driveプラグイン」、Claude向けには「Google Driveコネクター」として提示する。

```text
https://github.com/massuru-mi/personal-memory-os の公開済みセットアップ手順を読んで、
このアプリのGoogle Drive接続でPersonal Memory OSを初期構築してください。
ローカルPCのセットアップと定期実行は不要な構成にしてください。
保存先は［作成先フォルダのURL、または新しく作るフォルダの希望］です。
終わったら、読み戻して確認した保存先リンクと、このアプリの指示設定に貼る文章・登録先を提示してください。
```

現時点では、この手順を実行可能な配布セットは用意していない。仕様書の公開だけで初期構築が可能になったとは案内しない。

初期構築の処理は以下とする。

1. GitHubで公開済みのバージョンとcommitを固定し、その版の導入手順、配布ファイル一覧、テンプレートを読む。private repositoryの場合は読めるGitHub接続が必要。読み込めなければ推測で作らない。
2. 利用中のアプリのDrive接続が、フォルダ作成・一覧取得・通常ファイルの作成・内容更新・内容の読み戻しを実行できるか確認する。接続済みであることだけで書き込み可能とは判断しない。
3. 保存先、言語、タイムゾーン、記憶の保存方針を確定する。既存の指示・明確な設定があれば再質問しない。不明な場合はまとめて確認する。
4. 指定された保存先に既存PMOがあるか確認する。再実行時は読み戻して一致を確認し、足りないものだけ作る。同名の異なる内容や不明な所有者のファイルを上書きしない。
5. 私有vaultのSystem／Config／Dataディレクトリと、最初は空の生成ビューを配置する。MarkdownはGoogle Docsへ変換せず通常の`.md`ファイルとして、YAML／JSONも通常ファイルとして保存する。
6. 配布ファイル一覧に従い、内容と所有権、schema version、導入したcommitを記録する。公開版にはCLI互換の所有ファイルとハッシュを含む機械可読な配布マニフェストを用意する。ハッシュを推測したり、検証なしに整合性確認済みとしない。
7. Driveから配置結果を読み戻す。一覧がページ分割される場合は全ページ確認する。中断時は完了済みのファイルIDと未完了項目を報告し、再実行で同名の重複ファイルを作らない。
8. 保存先リンク、設定の要約、そのアプリ向けの指示文と登録先、最初の操作例をユーザーへ提示する。実際に取得したURLのみを使う。個人のDrive URLやIDは私有領域にのみ保存し、公開GitHubには書かない。

「初期構築して」という指示は指定範囲の作成を許可するものとして扱い、毎ファイル独自の確認を追加しない。ただしアプリやコネクターが要求する承認は尊重する。既存ファイルの衝突や依頼に含まれない変更がある場合は、その対象だけ説明する。

## カスタム指示

カスタム指示は短い入口とし、詳細ルールはvault内の`START_HERE.md`とConfigに置く。長いプロトコル全文を設定欄へコピーさせない。

生成する文章には実在するvaultと`START_HERE.md`への参照を埋め込み、以下を含める。

- 個人の文脈が必要なときにPMOを参照する。
- 明示的な記憶・訂正・整理の指示を、その範囲で実行する。
- それ以外は保存候補を会話中に提案する。承諾済みの自動保存方針がある場合はその範囲で実行する。
- 読み書きできなければ、実行済みのように答えない。
- ビューだけでなく原本と最新訂正を確認する。

文章案は[custom-instructions.ja.md](custom-instructions.ja.md)。初期構築の最後に個別の保存先を埋め込んで提示する。ChatGPT・Claudeの設定画面を自動で変更したとは言わない。指示文に使う接続の呼称と登録先だけを切り替え、記憶のルールは共通にする。

## 指示・提案・自動処理を分ける

初期設定案は「明示指示は実行、その他は提案」。以下は新しい仕様案であり、現行CLIの設定実装ではない。

| 会話 | 動作 |
|---|---|
| 「これを覚えて」 | 対象内容を原本へ保存し、結果を簡潔に報告 |
| 「前の理解は違う。正しくは…」 | 対応する訂正を保存。置き換え元が特定できればそのIDを記録 |
| 「MEMORYのこの部分を直して」 | 原本の追加・訂正を行い、該当ビューへ反映 |
| 「最近の記憶を整理して」 | 対象原本を読み、重複・矛盾を確認し、指示範囲のビューを更新 |
| 会話で新しい好みらしいものが出た | 「今後も使う好みとして保存しますか」など、具体的な保存内容を添えて提案 |
| 記憶の一覧が古い | 既に整理を依頼されていれば更新。そうでなければ会話中に更新提案 |
| 会話が行われていない | PMO単独では何も実行しない |

候補の意味が曖昧なら確認する。単なる言い換え・既存内容と同じ提案は繰り返さない。返事がないことを承諾としない。ユーザーが一定範囲の自動保存を希望したら、方針をConfigに記録する。自動保存方針と一覧の再生成方針は別の設定にする。

提案をチャット内だけに留めるか、私有`00_Inbox/MemoryCandidates`に残すかも保存方針で決める。ユーザーの指示なく、提案しただけの内容を確定記憶にしない。

Dailyも任意。会話の記録を有効にした場合だけ、そのチャットのファイルを更新する。将来実装では現行の`daily.enabled`などをCLIでも解釈し、設定名だけ存在する状態をなくす。

## MEMORYなどを手動で更新しても失われない方法

**ユーザーは「MEMORYを編集して」と頼める。内部では原本の変更として保存する。**

直接ビューだけを編集すると、後でCLIを使ったときに失われる。したがって次の手順に統一する。

1. 変更対象の原本IDと、現在有効な記憶・訂正を読む。
2. 意味を変更する場合は新しい原本を作る。同じ種類の古い原本を置き換える場合は`supersedes`を使う。履歴は残す。
3. 書き込みを読み戻して確認する。
4. 指示されたビューを、取得済みの原本から作り直す。生成の前後で原本の一覧・更新情報が変わった場合は再取得する。原子的な比較更新がないDrive接続では同時編集を完全には防げないため、完全防止とは説明しない。
5. 原本保存とビュー更新を分けて報告する。後半だけ失敗した場合に原本を再作成して重複させない。

見出しや並び順の好みはConfigの表示方針に記録する。情報の追加・訂正と、見た目だけの調整を分ける。再生成前にビューだけの未取り込み編集を見つけた場合は黙って消さず、その差分を示す。この検出機能は今後実装する。

## 定期再生成に依存しない読み取り

生成ビューは便利な要約であり、最新性を保証する原本ではない。クラウド運用では必要な会話のタイミングで以下を行う。

- 最新の訂正と関連する原本を確認してから、ビューを文脈として利用する。
- 取り消し・置き換えを解決するため、対象IDを参照する後続レコードも確認する。
- 全体ビューを再生成する際は対象ディレクトリを全件取得する。検索結果の上位数件を全件とみなさない。
- ファイル取得漏れ、同期途中、壊れたレコードがあれば、完全な一覧として上書きしない。確認できた範囲と未確認部分を明示する。
- ビューの更新日時だけでは最新性を判定しない。将来、原本IDと内容のハッシュを含む生成元情報を保存し、CLIとクラウドで共通利用する。

原本を読んで回答することと、ファイルを書き換えることは別。最新情報を利用するためだけに、常に全ビューを書き換える必要はない。

現在の`START_HERE.md`はビュー優先の読み順であり、この手順への移行は未実装。クラウド機能を公開する前に、adapter・プロトコル・CLIの生成元情報をまとめて整合させる。

## ローカルCLIとの互換性

クラウドとローカルで同じschema、同じ原本、同じ有効性判定を使う。異なるデータストアやGoogle Docs専用形式を導入しない。ローカルCLIは高速な再生成・FTS検索・検証・バックアップを追加する選択肢とする。

ローカルを後から使う場合も、既存vaultへ`install`を再実行して上書きする案内はしない。配布マニフェストとバージョンを読み取り、内容検証後に既存vaultとして扱う導線を設ける。所有情報が欠けている場合は自動修復したことにせず、何を信頼して引き継ぐかを示す。

システム更新はユーザーの依頼時にGitHubの新旧版を比較して提案できる。新リリースを背景で監視する処理は別機能。クラウドで更新する場合も、対象版の固定、変更検出、私有バックアップ、Configの保存、Data非上書きが必要。

## 実装状況と受け入れ条件

記憶の整合性について実装した修正：

- `supersedes`を解決し、古い記憶・訂正を現在のビューから除外する。履歴ファイルは変更しない。
- MEMORYとNOWで設定された確信度を共通利用し、採用された推測にラベルを付ける。採用されない推測が既存の明示記憶を隠すことも防ぐ。
- 保存・Markdown読み込み・doctorで共通の項目検証を使う。タイムゾーンなし日時や必須項目欠損を拒否する。

クラウド経路の実装前に必要なもの：

1. 固定版の配布ファイル一覧・ハッシュと、機械可読なbootstrap手順。
2. Driveフォルダと通常ファイルの作成・更新・読み戻し、途中再開の検証。
3. カスタム指示生成と、保存・提案・Daily・ビュー更新のConfig定義。
4. adapterと`START_HERE.md`を、原本の鮮度確認を含む読み順へ更新。
5. クラウドとCLIの共通テスト用vaultで、置き換え・推測・訂正の結果が一致すること。
6. ChatGPTとClaudeアプリのそれぞれで、PCのセットアップなしに「初期構築→記憶追加→別会話で参照→訂正→一覧更新」を完了する実機確認。
7. ChatGPTで初期構築→Claudeで参照・訂正、およびClaudeで初期構築→ChatGPTで参照・訂正の両方向を確認する。古い記憶が復活せず、vaultが重複しないこと。
8. 途中でローカルCLIを使っても原本やユーザー変更が消えないこと。

既知の残課題：マニフェスト欠損時の保護、Windowsのtzdata依存、検索インデックスの鮮度、turn取り込みの部分保存・再試行、Dailyの読み取りを含むロック。これらを修正済みと扱わない。

## 調査した前提

公式資料では、会話をまたぐ設定をカスタム指示に置くこと、外部操作に対応するプラグインが必要なことが説明されている。プラン・workspace・接続によって利用可能な機能は異なる。

- [OpenAI：Prompting](https://learn.chatgpt.com/docs/prompting)
- [OpenAI：Plugins](https://learn.chatgpt.com/docs/plugins)

設計時に参照したGoogle Driveプラグインにはフォルダ作成、通常ファイルのアップロード、内容更新、読み取りのツール定義があることを確認した。ツール定義の確認は、対象ユーザーのDriveでの成功確認ではない。Driveへの接続テストや書き込みは未実施。


Claudeについては、[Google Workspaceコネクターの公式説明](https://support.claude.com/en/articles/10166901-use-google-workspace-connectors)でフォルダ作成・任意形式のアップロード・生成ファイルのDrive保存が説明されている。生成ファイルの保存にはコード実行・ファイル作成機能が必要とされる。[個人設定の公式説明](https://support.claude.com/en/articles/10185728-understanding-claude-s-personalization-features)ではプロフィール指示とプロジェクト指示の適用範囲が分かれている。

これはClaude側でMarkdown原本の作成から既存ファイルの内容更新・読み戻しまで確認済みという意味ではない。検索だけ可能な接続やGoogle Docs編集だけ可能な接続を、PMOに必要な通常ファイル操作と同一視しない。Cloud-only対応の確認はアプリ・接続ごとに行う。機能が不足する場合、足りない操作を明示し、対応するクラウド接続を案内する。黙ってClaude CodeやローカルPC必須の手順へ切り替えない。
